Bytasm fixture build information
================================

All fixtures are compiled from C source written for Bytasm (fixtures/src/).
Their authorisation basis is owned_or_built. None of them is ever executed:
not by Bytasm, not by its tests, and not by the build script.

Rebuild:  ./fixtures/build/build.sh   (or: make fixtures)
Verify:   make verify-fixtures        (checks bytes against MANIFEST.sha256)
CI never rebuilds fixtures. It checks and reads the committed bytes.

Built on 2026-10-26 on macOS 27.0.1 (Apple Silicon host), Docker Desktop
29.8.1. Rebuilds are byte-identical; see "Reproducibility check" below.
SOURCE_DATE_EPOCH=1761436800 and -ffile-prefix-map are set to reduce variance.

Reproducibility check (2026-10-26)
----------------------------------

- The final build.sh was run 8 times in a row; every run succeeded and
  produced the same MANIFEST.sha256 (all 8 files byte-identical). The four pre-existing files
  (AArch64 ELF and the x86-64 .o) kept their previous hashes.
- The cross-toolchain image was also rebuilt with `docker build --no-cache`
  (fresh download of every package from the snapshot). It installed the same
  package set, and the fixtures it compiled were byte-identical.
- One build-script fix came out of this: `rm -rf` on build/out/ followed by
  a bind mount intermittently failed on Docker Desktop ("cannot open output
  file"), so build.sh now empties build/out/ in place instead.


AArch64 status
--------------

Built and validated (header checked with llvm-readelf, parsed by LIEF 1.0.0,
covered by tests). Completed well within the half-day time box because a native
arm64 GCC toolchain was already available locally. Note: this is the fixture's
*target* architecture. It is unrelated to the host or container architecture
that runs Bytasm.


Open items
----------

- The AArch64 files still use the borrowed ruby:3.1.2-bullseye image. They
  were left untouched so their committed hashes stay valid. Moving them to
  the pinned image (for example, by adding the native arm64 gcc to
  build/Dockerfile) would change their bytes and needs a manifest update in
  the same change.
- The x86-64 .o still uses the host's Apple clang, which is not pinned.
- After rebuilding with any new toolchain, regenerate MANIFEST.sha256 in the
  same change (build.sh does this) and update this file.
