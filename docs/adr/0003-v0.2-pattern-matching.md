# ADR-0003: v0.2 pattern matching — strings, YARA-X, worker, and run model

- **Status:** **Proposed** (2026-10-27), pending the owner's review. Implemented on branch `feat/v0.2-yara-x-rules`; nothing here is accepted until reviewed.
- **Scope:** v0.2 (milestone M6, blueprint §12): the built-in strings extractor, YARA-X with Bytasm's own rules, multi-step analysis runs processed by a background worker, `partial`, cancel, findings with byte evidence, findings in the JSON report. Does not change the input policy, the gate I1 design, or any decision in [ADR-0001](0001-stack.md) or [ADR-0002](0002-v0.1-implementation-choices.md).

## Context

Blueprint §3 puts in v0.2: a strings extractor, YARA-X with a small self-written rule set, `finding` + `evidence`, a findings table with an evidence drawer, a background worker with multi-step runs, `partial` status, and cancel. §5.4.2 deferred the worker choice ("Procrastinate or a hand-rolled claim loop", both on PostgreSQL). Blueprint §5.4 plans PostgreSQL, but ADR-0001 §7 records the database as "undecided as a formal decision"; [ADR-0002](0002-v0.1-implementation-choices.md) (accepted) chose SQLite for v0.1 and *expected* the v0.2 worker to require PostgreSQL. No accepted document requires PostgreSQL for v0.2.

The implementation is on branch `feat/v0.2-yara-x-rules`; [`milestones/v0.2-pattern-matching.md`](../milestones/v0.2-pattern-matching.md) lists each v0.2 criterion and its status. Choices it had to make:

## Decisions

| Topic | Choice | Why | Consequence |
|---|---|---|---|
| YARA-X version and binding | **`yara-x` 1.22.1** (PyPI, pinned `>=1.22.1,<1.23` in `backend/pyproject.toml`, locked with hashes in `uv.lock`), used through its **official Python module `yara_x`** | Blueprint §5.6. Prebuilt `cp39-abi3` wheels exist for manylinux_2_28 x86_64 and aarch64 and macOS arm64/x86_64 (PyPI file list, 2026-10-27), so the Docker image (Debian trixie, glibc 2.41) and CI need no Rust toolchain. | The module is imported **only inside the adapter child** (`bytasm.adapters.yara_x_scan`), after it lowers its rlimits, exactly like LIEF. |
| Where YARA-X runs | A **separate, resource-limited child process** (`python -I -m bytasm.adapters.yara_x_scan`), started by the **worker** for scans and by the **API** only to compile the rule set (no sample bytes). Same runner, limits, env and output caps as v0.1 (blueprint §5.4.1, §5.6). | Keeps "the API never parses" (§5.1 boundary 2) and "every tool is a subprocess" (boundary 3). | Process and resource separation, **not a sandbox**: same user, same data volume, same network as its parent. |
| Worker and database | **Hand-rolled claim loop on the existing SQLite database** (`bytasm worker`), one per data directory (`flock` on `data/worker.lock`). WAL journal, foreign keys on, 30 s busy timeout. Each transition is one conditional `UPDATE … WHERE status = <from>`. | Single local user, low volume, no new service, credentials or dependency. SQLite serialises writers, so the conditional update is the claim. **This departs from ADR-0002's expectation of PostgreSQL** and from §5.4.2's "both keep jobs in PostgreSQL"; the property §5.4.2 asks for (run and job created in one transaction) still holds, because the run row *is* the job. | No `LISTEN/NOTIFY`: the worker polls every 0.5 s. Not designed for several workers or hosts. Tested: conditional claims and transitions, API and worker as separate processes on one file, restart recovery, atomic migrations. Not tested: durability under power loss, many concurrent writers. Moving to PostgreSQL later changes the engine, the claim query (`FOR UPDATE SKIP LOCKED`) and migrations, not the lifecycle. |
| Steps | Profile `default-static` (snapshot version 2): **strings**, then **yara-x**, each in its own resource-limited child process. LIEF metadata is not a run step: the import already read it from the same bytes. Admission (input policy, blob SHA-256 and size) is re-checked **before every step**. | Blueprint §3 ("multi-step runs"), J5 ("sequential steps, per-step timeout"). | A failed or timed-out step does not stop the next one (YARA-X does not depend on strings); a cancel, a failed admission check or a stopping worker ends the run there. |
| Run lifecycle and `partial` | `queued → running → succeeded | partial | failed | cancelled`, `queued → cancelled`. Step: `succeeded`, `failed`, `timed_out`, `cancelled`, or `skipped` (no invocation). `partial` = at least one step kept results and another did not; `failed` = none kept results. Results of finished steps survive a later failure. Runs left `running` by a stopped worker are finished from their committed steps at the next start (`partial`/`failed` with `worker_interrupted`). | Blueprint §3, §7.3 (partial banner, cancelled "with what had finished"), §9.1 ("Timeout in one step → run `partial`"). "Partial output is never used" (§5.4.1) applies per step: only a validated result of a successful child is stored. | A run never stays `running` and is never `partial` without a preserved result. Fixed texts explain which steps are missing (UI banner and report). |
| Cancellation | Queued: the API cancels at once. Running: the API sets `cancel_requested` (and `cancel_requested_at`); the worker polls it every 0.25 s during a step and between steps, sends SIGTERM then SIGKILL to the child's process group, and records the step `cancelled`. A step's results are stored by a transaction whose first statement is a conditional `UPDATE` requiring no cancel; in SQLite it also takes the write lock, so a cancel either precedes it (nothing stored) or waits for it (the step's results are kept, later steps are not run). The final status update is conditional too, so a late cancel still ends the run `cancelled`. | Blueprint §5.4.2 "Cancellation design", §7.3. | Tested: queued cancel, running cancel (child PIDs gone), cancel between steps, during validation, after the last commit, a cancel racing a timeout, worker stop. |
| Strings extractor | Bytasm's own adapter `strings_extract`: printable ASCII (0x20–0x7E, tab) and UTF-16LE runs of the same characters, ≥ 6 characters, any alignment; at most 5,000 strings (first by offset) and 256 characters per value, with totals and full lengths reported; sorted by (offset, encoding). The parent checks every item against the file's bytes. Stored as `string_occurrence` rows; exported in the report as counts only. | Blueprint §3.1 ("ASCII and UTF-16LE strings with offsets, min length 6"), §5.1 boundary 3 ("This holds for the in-house strings extractor too"), §6. | Strings are observations, never findings or labels. Non-ASCII UTF-16 text is not extracted. |
| Raw output and report | `GET /invocations/{id}/raw` serves a step's validated, content-addressed `result.json` (never sample bytes or stdout/stderr), re-hashed first. The JSON report moves to schema version 2 with `pattern_analysis`: the newest `succeeded`/`partial` run, its steps, rule set, string counts and findings with evidence. | Blueprint J6 ("raw output download"), J9 ("findings with evidence (v0.2)"). | Version-1 fields are unchanged. String values stay out of the report. |
| Rules ownership | **Bundled and read-only.** `rules/yara/*.yar` (one rule per file, file name = rule identifier) plus `rules/yara/ruleset.json` (name, version). They are copied into the image. There is no API, UI, environment variable, or request field to add, edit, or point at other rules. | Blueprint §3.1 ("YARA-X with a small self-written rule set", "Bytasm rule set"), §8.2 ("Tool rules are baked into the image at build time"), §13.2 (`rules/yara/`). User-authored rules are not in the accepted scope. | The UI shows the rules and can **validate** (compile) them; it cannot create or edit them. Changing rules is a code change, reviewed like any other. |
| Rule versioning | The rule files are joined into one canonical **snapshot** whose SHA-256 identifies the rule set. Each run stores the rule-set row (`rule_set`: name, version, SHA-256) in its profile snapshot, and the snapshot bytes are kept in the content-addressed outputs store. | Blueprint §6 (`rule_set`, "snapshot of the profile, tool versions, and rule-set hashes"). | Editing a rule after a run creates a new rule-set hash; the earlier run still shows and links the exact text it used (tested). |
| Compiler settings | `Compiler(includes_enabled=False)`; one `add_source` per file with `origin=<file name>`; diagnostics reduced to YARA-X's `code`, `title`, file, line, column (at most 20 each). | `include` would read arbitrary files. YARA-X's full diagnostic `text` quotes source lines; only short fields are needed. | Includes in a rule file are a compile error (E044, tested). |
| Scan bounds | `Scanner.set_timeout(20)` (below the parent's 30 s wall-clock kill), `max_matches_per_pattern(1000)`; the adapter keeps at most 32 rules, 32 patterns per rule, 20 evidence items per pattern, and a 32-byte hex excerpt per match. The parent re-validates all of this with a strict schema. | Bounded output and storage. | A finding records `match_count` and `evidence_truncated`. |
| Evidence | Only what YARA-X 1.22.1 documents per match: `offset`, `length` (bytes from the start of the scanned data), `xor_key`. The excerpt is read by the adapter from the admitted bytes; the worker rejects the whole result unless every range lies in the file and every excerpt equals the file's bytes there. | Blueprint §9.1 "Finding ↔ evidence" invariant. | No section name, virtual address or "highlight" is derived yet. |
| Admission before YARA-X | The worker re-runs the input policy on the sample's SHA-256, re-reads the stored blob and checks its SHA-256 and size against `sample_version`, and checks the rule snapshot's SHA-256, **before** starting the child; the child re-checks both hashes before compiling. The API does the policy and blob checks too when a run is created. | The admission rules in blueprint §3.4 apply to every parse, not only to imports. | A missing/changed blob or a sample the current policy does not admit ends the run as `failed` without starting YARA-X (tested with a spy child). |
| Compose | A second service, `worker`, from the same image and with the same hardening as `api` (non-root, `cap_drop: [ALL]`, `no-new-privileges`, read-only root, limits, `init`, `noexec` `/tmp`, only the named data volume), **no published port**, healthy while its heartbeat file is fresh. | Blueprint §5.7 ("A `worker` service is added in v0.2"). | `make compose-check` asserts both services and that only `api` publishes a port; `scripts/check-container.sh` checks both running containers. The worker still holds the database: per §5.4.1 it **does not** satisfy gate I1. |
| Migrations | Migration `0002` adds the v0.2 tables and columns; existing v0.1 rows become `kind = "import"` runs. Bytasm now runs migrations in one explicit transaction with foreign-key enforcement switched off and `PRAGMA foreign_key_check` before commit. | SQLite batch migrations copy and drop referenced tables; Python's `sqlite3` does not wrap DDL in its implicit transactions. Found when the v0.2 image met a real v0.1 volume. | Tested: 0001 → 0002 → 0001 → 0002 with data, and a failing migration leaves the schema unchanged. |

## YARA-X facts this relies on (verified 2026-10-27)

From the official Python API page (<https://virustotal.github.io/yara-x/docs/api/python/>), the `yara_x.pyi` stubs at tag `v1.22.1` (<https://github.com/VirusTotal/yara-x/blob/v1.22.1/py/yara_x.pyi>), PyPI metadata (<https://pypi.org/project/yara-x/1.22.1/>), and by running the pinned package:

- `yara_x.Compiler(relaxed_re_syntax=False, error_on_slow_pattern=False, includes_enabled=True)`; `add_source(src, origin=None)` raises `yara_x.CompileError` and records the error in `errors()`; `warnings()`; `build()` returns `Rules`; iterating `Rules` yields rules with `identifier`.
- `errors()` / `warnings()` return dicts with `type`, `code`, `title`, `labels`, `text`; with the pinned version they also carry `line` and `column` (observed, used only if they are non-negative integers).
- `yara_x.Scanner(rules)`, `set_timeout(seconds)`, `max_matches_per_pattern(n)`, `scan(bytes)`; raises `yara_x.ScanError` / `yara_x.TimeoutError`.
- `ScanResults.matching_rules` → `Rule` (`identifier`, `namespace`, `tags`, `metadata` as `(identifier, value)` pairs, `patterns`) → `Pattern` (`identifier`, `matches`) → `Match` (`offset`: file offset of the match; `length`: length in bytes; `xor_key`: key or `None`).
- **Licence:** BSD-3-Clause (repository `LICENSE`, three clauses; PyPI classifier "BSD License"). A permissive licence; compatible with any licence Bytasm may choose, with attribution. Bytasm's own licence is still undecided (blueprint §13.2), so a formal licence review of the whole dependency set remains open.
- **Not verified:** whether YARA-X's scan timeout bounds every module's parsing time (the parent's wall-clock kill is the backstop); behaviour of `math.entropy` beyond the data (not used); an official security statement about scanning untrusted input with the Python binding (none found; Bytasm's input policy applies regardless).
