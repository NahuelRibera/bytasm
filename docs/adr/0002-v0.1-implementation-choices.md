# ADR-0002: v0.1 implementation choices left open by the blueprint

- **Status:** Accepted (2026-10-27). The "Container mode" row was added later the same day and is **proposed**, pending the owner's review.
- **Scope:** v0.1, milestones M2–M5. Does not change any decision in [ADR-0001](0001-stack.md) or the input policy and security boundaries of [`PROJECT_BLUEPRINT.md`](../PROJECT_BLUEPRINT.md) revision 0.3.

ADR-0001 §7 lists choices the blueprint leaves as recommendations. This ADR records the smallest maintainable option chosen for each one that M2–M5 needed. None of them is a security control; where a choice affects a blueprint release-gate item, the consequence is stated.

## Decisions

| Topic | Choice | Why | Consequence |
|---|---|---|---|
| Database | **SQLite** (one file in the data directory), SQLAlchemy 2.x + Alembic as decided in ADR-0001 | Single local user, a single server process, no concurrent writers. No extra service to start, no credentials to hold. The ORM and migrations keep a later move to PostgreSQL (v0.2 job queue, §5.4.2) a contained change. | The v0.2 worker decision (Procrastinate or a PostgreSQL claim loop) will need PostgreSQL; that migration is v0.2 work. 64-bit unsigned addresses are stored through a small `U64` column type. |
| How v0.1 runs locally | **Two ways.** `make compose-up` (recommended): one `api` service in `compose.yaml`, built from `Dockerfile` on the same pinned `ghcr.io/astral-sh/uv` image that `make check-linux` uses, serving the built UI. `make serve`: natively, for development. Both are fixtures-only by default and serve `127.0.0.1:8000`. | The container is where blueprint §5.7 runs the parser, because its limits are tested on Linux. One service is enough: SQLite replaces `db`, and the API serves the UI, so no `web` service. The UI is built on the host, so the image needs no Node base image. | Blueprint §12.1's Compose items are met and asserted by `make compose-check` (configuration) and `scripts/check-container.sh` (what the kernel applied). Settings: `127.0.0.1:8000:8000`, `user: 10001:10001`, `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges:true`, `mem_limit`/`memswap_limit` 2g, `cpus: 2`, `pids_limit: 128`, `init: true`, one named volume at `/data`, a 64 MiB `noexec` `/tmp`, default seccomp, no Docker socket, no host mounts. Outbound network is not restricted (blueprint §8.2, v0.1 row). On macOS, native runs stay fixtures-only because `RLIMIT_AS` cannot be applied. |
| Container mode (security-relevant) | The image sets `BYTASM_CONTAINER=1`. In this mode the server listens on `0.0.0.0` **inside the container's network namespace**, the request guards skip only the "connection arrived on a loopback address" check, and `self_built` is refused. The Host, Origin and `X-Bytasm-Request` guards are unchanged. The mode is refused unless a container runtime marker (`/.dockerenv` or `/run/.containerenv`) exists, and `BYTASM_HOST` cannot be set with it. | Docker can only forward a published port to an address on the container's own interface, so a loopback-only listener is unreachable. Blueprint §8.2 places the v0.1 binding control on the published port ("Ports published on `127.0.0.1` only"); `make compose-check` asserts it. `self_built` must be refused on a non-loopback binding (blueprint §5.4.1, §5.7), and inside the container the listener is not loopback. | The container's interface is reachable from the Docker host and its bridge network; there is only this one service on the project network. The Host allowlist still blocks DNS-rebinding and foreign-origin browser requests, but raw HTTP clients that reach that interface can set any `Host`. Running `self_built` in the container would need a separate decision (for example a loopback listener plus an in-container proxy, which only moves the same trust). **Flagged for the owner's review.** |
| Where the UI is served | The API serves the built SPA (`frontend/dist`) from its own origin | Same origin means the UI needs no CORS permission, and the API grants none to anyone. | `npm run dev` (Vite, port 5173) proxies `/api` and rewrites `Origin` to the API's own; it is for UI development only. |
| Frontend libraries | React + TypeScript + Vite, TanStack Query. **No** router library (four screens, a 50-line history router), **no** TanStack Table or React Aria (plain semantic `<table>`, native form controls, a small ARIA tab list). Plain CSS with custom-property tokens. | Fewest dependencies that meet blueprint §5.2/§7.4 for v0.1's screens. | Revisit when v0.2 adds sortable/filterable findings tables. |
| API client | Hand-written typed client (`frontend/src/api.ts`) mirroring `backend/src/bytasm/api/schemas.py` | v0.1 has 12 endpoints; generating a client adds a build step and a dependency. | Types can drift from the backend; the Playwright tests exercise the real API to catch that. |
| Report schema source | Pydantic models in `bytasm/reports/model.py`; `schemas/report.schema.json` is generated (`make schemas`) and a test keeps it identical | One source of truth; the generator validates every report against the same models before export. | — |
| Source revision in reports | `git describe --always --dirty --abbrev=40`, read once at start-up. The image has no `.git`, so `make compose-build` passes the same value as the `BYTASM_SOURCE_REVISION` build argument. `image_id` stays `null`: the container cannot learn its own image ID without access to Docker. | Blueprint §2 J9 asks for the git commit and image ID. | Reports from an uncommitted checkout say `-dirty`. A plain `docker compose build` (without `make`) records no revision. |
| Dependency audit | `pip-audit` 2.10.1 in its own `audit` dependency group in `uv.lock`, run by `make audit` with `--strict --require-hashes --disable-pip` over `uv export --locked --all-groups` (runtime, dev and the audit tool itself), followed by `npm audit --audit-level=high` | Reproducible: the tool and everything it audits come from the lock file. A separate group keeps it out of the normal `uv sync`. | Both audits query public advisory data (PyPI/OSV, the npm registry) with package names and versions. |

## Not decided here

PostgreSQL migration and the job queue (v0.2), `self_built` inside the container, licence, and anything under gate I1 (a separate analyzer container with `network_mode: none`).
