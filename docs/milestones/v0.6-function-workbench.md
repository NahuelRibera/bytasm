# v0.6: evidence-led function workbench

## Requirements and architecture map (before implementation)

Baseline: clean main, 277d36d, merged PR #9 confirmed through read-only GitHub
inspection. Existing SQLite/file queue, transactional tool outputs, immutable
annotations/citations, baseline comparisons and report schemas 2/3/4 must survive.
LIEF imports, strings, bundled YARA-X and pinned capa already exist. Ghidra 12.2 /
JDK 25 is optional and caller-installed; offline non-root Linux execution uses
fresh projects, fixed scripts, process groups, cgroups and bounded tmpfs.
Existing function detail is first-16 only; inventory stops at 256; search only
matches names. Existing graphs are static per-function call-site illustrations,
not interactive program graphs. Existing explanations deliberately infer no
behavior from names. Old milestone verification is historical, not current proof.

P0 planned vertical slices:

1. Inventory discovery: exact name/namespace/address and bounded substring search,
   stored facets, deterministic ordering, identity-bound cursors, explicit
   completeness and response budgets; retain offset compatibility.
2. Explicit selected-function jobs: at most eight verified inventory entries,
   immutable source provenance, exact-identity reuse, existing queue/cancellation
   and retry lifecycle. A deliberate request performs a fresh bounded Headless
   import; search and opening stored evidence never launch a parser. No persistent
   Ghidra project cache is trusted. Larger default inventory is bounded at 1024.
3. Beginner overview: file/run scope, exact retained detail/instruction/call counts,
   no reviewed behavior hypothesis, availability and caps, export privacy notice.

P1 candidates only after P0 verification: linked one-hop static call tables;
function-level analyst workspace. Defer Ghidra matching/comparison, arbitrary-file
intake, global search, backup/restore, richer data/non-call references and maps
without exact source records. Existing version annotations/comparison stay intact.

I1 remains blocked: API-side LIEF parser, shared writable app/database volume,
same-kernel trust and unverified host isolation cannot be fixed by an upload UI.
Fixtures and existing Linux self_built admission remain unchanged. No AI, sample
execution, external sample lookup or new dependency is authorized by this design.
No binary/JDK distribution is added; ida-settings distribution blocker remains.
No migration is needed for immutable run snapshots and content-addressed output.
Historical report schemas 2/3/4 must remain byte-identical. New UI must use escaped
text, keyboard controls, bounded tables, visible focus and 360px layouts.

## Architecture and user journeys

`function_inventory.py` searches only a verified immutable result. Scope includes
project/version/hash/run/invocation/output/tool/profile/script; original indices
remain evidence identities despite display sorting. Cursors are checksummed
scope tokens, not signed authorization. A zero filtered result is not evidence
of whole-program absence. The `has_calls=false` facet means no retained calls.

`function_selection.py` serializes exact-set lookup and queue creation with
SQLite BEGIN IMMEDIATE, rechecks admission/blob identity and verifies cached
successful output. A selected job uses the same single active version-run rule,
worker recovery, commit condition, cleanup and cancellation as baseline runs.
Selection data is bounded JSON in a private fixed path, never a command/script.
No writable Ghidra database is cached or shared. API reads never launch parsers.
A queued job whose script/profile changed fails rather than mixing identities.

The beginner imports an admitted fixture, runs the optional provider, reads the
scoped overview and limits, searches retained identity fields, opens stored
pseudocode, and uses the explicit request action when a different function needs
details. The new run page shows progress/cancellation and links back to its source.
The analyst can select across pages, inspect at most eight entries per request,
expand retained one-hop calls through the table, inspect exact addresses/bytes,
follow invocation JSON pointers and export the selected run. Existing version
annotations are available separately; exports do not claim to include those notes.

Pseudocode is reconstruction, not original source. Body size is Ghidra's count of
addresses, possibly discontiguous. Ghidra can reconstruct pseudocode for an entry
with no retained instruction listing; the interface says so instead of inventing
assembly. Calls cover at most 64 instructions and 64 direct references per detailed
function. Unknown/interior targets are never assigned to a function heuristically.

## Summary, hypothesis and recommendation rules

Counts and statuses derive from verified records only. Detail counts use retained
inventory as denominator; no percentage is emitted. Ghidra is the only selected
tool in this run, so its success cannot imply strings/YARA-X/capa coverage.
Unavailable output has unknown total, not zero functions. Valid empty output is
separate from failed/cancelled/unsupported/unavailable output. Inventory caps and
per-function truncation are explicit; missing matches do not establish absence.

No reviewed Ghidra behavior hypothesis was added. UI explicitly says no reviewed
behavior explanation is available. Hypotheses stay empty in exports; analyst
conclusions are not fabricated. Recommendations preserve the original, request
missing supported static work when partial/failed/capped, and advise qualified
review and not running an unfamiliar file on an everyday machine. No score,
verdict, probability, execution instruction or safety promise is introduced.

## Bounds, privacy and remaining isolation risks

Ghidra 12.2/JDK 25 and the existing native PE x86/x64 and little-endian ELF
x86/x64/AArch64 allowlist remain. Mach-O, managed PE, archives, raw shellcode and
other architectures are refused. Native macOS/Windows sample analysis remains
unavailable; no platform parity is assumed. Exact real verification follows below.

Resource limits stay at 180 seconds parent wall time, 60 seconds Ghidra analysis,
768 MiB JVM heap, 2 MiB result, 64 KiB captured streams and at most 1024 function
records. Per-function output is 4096 pseudocode characters, 64 instructions,
32 bytes/instruction and 64 direct call references. Selected requests cap at eight.
The existing offline non-root Linux, dropped-capability/no-new-privileges, bounded
cgroup/tmpfs controls remain mandatory. Output overflow is failure, never silent
success. Exports are capped at 16 MiB and warn about symbols/pseudocode/paths.

This is not a complete sandbox. API import parsing still has outbound access,
worker and API share writable application state, and same-kernel/container/parser
compromise remains a risk. No real cgroup escape, tmpfs exhaustion/OOM campaign,
power-loss recovery, every analyzer failure or restart during serialization was
verified by this increment. Existing synthetic flood/crash/restart tests do not
establish those stronger claims. No sample or derived content is sent to a service.

## Deployment-boundary finding and correction

A real browser flow with a network-disabled Ghidra worker, private `/data/tmp`
tmpfs and a separate persistent `/data` volume exposed an inherited failure:
ContentStore.put_bytes assumed scratch and output storage shared a filesystem.
Ghidra completed, but EXDEV on atomic rename discarded the result transaction.
Earlier real-provider tests used one tmpfs for both locations and missed it.

Storage now catches only cross-device rename for already hash-verified output,
stages those bytes in the private destination shard, flushes them and publishes
with an atomic same-filesystem rename. Other I/O failures remain failures. Normal
and failed paths remove staging; the existing age-based startup sweep removes
only old regular files with the reserved staging-name pattern, preserving fresh
files, symlinks and unrelated files. No parser-owned directory/project is copied.
This does not provide a general quarantine transfer protocol or pass I1.
Regression tests cover cross-device success, no partially replaced final file,
destination failure, duplicate content and stale/fresh/unrelated staging.
