Notable gaps found by reading the code:

1. **No address-space bridge.** Ghidra addresses were tool text, explicitly
   never converted to offsets (correct). But that meant capa VAs, YARA file
   offsets, string offsets and Ghidra functions could not be related exactly.
   ghidra-3 does not report Ghidra's image base. Ghidra loads ELF PIEs at
   `0x100000` while LIEF declares `0x0`, so any join based on Bytasm's own
   assumption about the base would be wrong for ELF.
2. Correlation existed only inside Ghidra (calls/references). Findings from
   other tools were only grouped per sample.
3. Guided explanations were per tool. They could not say "this capa match is
   *at* this function, which references *this* import".

## 2. Selected scope and justification

Three connected workstreams, in the user's preferred order. Priority 3 came
first in time because it is a prerequisite:

1. **Analysis expansion (prerequisite): Ghidra protocol `ghidra-4`.** The
   extractor now reports `image_base` and Ghidra's memory blocks, with the
   file-byte ranges Ghidra itself mapped (`MemoryBlockSourceInfo` /
   `FileBytes`). Bytasm translates a Ghidra address to a file offset only
   through these tool-reported ranges, never by assuming a load base.
2. **Evidence correlation and navigation**: a deterministic typed graph
   (`evidence_graph.py`) over LIEF + Ghidra + strings + YARA-X + capa, with
   exact relationship types, strengths, translation basis, deduplicated
   locators and per-join coverage.
3. **Dual-layer interpretation**: Understand claims (`evidence_understand.py`)
   built only from graph edges and citing them by ID; the Investigate view
   pages the same graph. Coverage and layout are visualization-ready.

## 4. Evidence model

Backward-compatible additions only. **No database migration.** The graph is a
derived, deterministic view computed from stored, revalidated outputs:

- Ghidra output: hash-verified, size-capped (2 MiB) and provenance-checked by
  the existing `api.ghidra._read`.
- Findings/evidence/strings: existing rows of the selected pattern run.
- Structure: the version's single import record.

Nodes carry a stable ID (`kind:` + SHA-256 prefix of the exact identity), the
untrusted `label`, the exact `identity`, the Ghidra `address` (space and
text), the `file_offset` with `file_offset_basis` and `file_offset_state`,
typed attributes and source locators (tool, version, run, invocation, output
digest, pointer). Edges carry `type`, `strength`, `basis[]`, deduplicated
locators (≤8, with count and truncation) and attributes. Large reports are not
copied into the database. The graph is cached in-process per scope digest.
See `docs/api-v0.10-evidence.md` for every field.

Distinctions kept explicit:

- *Declared* (LIEF section/entry/import declarations), *tool-reported*
  (Ghidra references, memory map; capa/YARA matches), *derived* (exact offset
  equality, containment), *coarse* (name equality).
- RVA vs VA vs file offset: PE section rows store RVAs. `DeclaredLayout` adds
  the declared ImageBase, and `va_to_file_offset` refuses VAs before the base
  is known. PE raw bytes beyond VirtualSize are not treated as loaded. ELF
  non-ALLOC sections get no address. Ghidra places them in their own overlay
  spaces, which the space-aware map keeps separate from `ram`.
- Six translation states; only `mapped` has a value.

### ghidra-4 protocol

`schema_version: "ghidra-4"`; adds top-level `image_base` (required),
`memory_blocks` (≤64; name, start, end, r/w/x, initialized, `file_ranges` ≤16
with `file_offset` and provenance `ghidra_memory_block_file_bytes`) and
`memory_blocks_truncated`. Validators reject v4 fields under older versions and
cross-space ranges. File ranges beyond the admitted bytes are discarded at
translation time, and the discard is reported. The serializer still emits
historical shapes for ghidra-1/2/3. Schema: `schemas/ghidra-analysis-v4.schema.json`
(the v3 file is unchanged). New Ghidra runs must produce ghidra-4. Stored
ghidra-1/2/3 outputs stay readable, and their translation-dependent joins are
reported `unavailable`.

## 5–7. Understand and Investigate contracts

One graph, two readings. The full contract is in `docs/api-v0.10-evidence.md`.

- **Understand** (`GET /sample-versions/{id}/evidence`): claims (title, plain
  summary, technical statement, subjects, cited edge IDs, source locators,
  reviewed interpretation and alternatives where available, limitations,
  completeness, navigation target), coverage, layout, limitations.
- **Investigate** (`/evidence/nodes`, `/evidence/edges`,
  `/evidence/nodes/{id}`): cursor-paginated, deterministic, filterable typed
  nodes/edges; node neighborhoods ≤256 edges; every edge cites raw-output
  pointers.

A claim never introduces information that its cited edges lack. Generated
sentences contain no untrusted text: names and string values remain node
labels. Static wording is enforced ("contains a reference", "does not show
that the code ran").

## 8. API changes

Added (read-only): `GET /api/v1/sample-versions/{id}/evidence`,
`…/evidence/nodes`, `…/evidence/edges`, `…/evidence/nodes/{node_id}`.

Modified: Ghidra runs now emit `ghidra-4`. `/runs/{id}/ghidra/functions/{i}`
returns `protocol_version: "ghidra-4"`. The run export maps ghidra-4 to
`bytasm-ghidra-report-2` like ghidra-2/3. The limitation text says
"ghidra-3 or later". No historical contract changed.

## 9. Safety

- Read-only endpoints; no tool execution, sample access or file writes.
- New extractor output is bounded (64 blocks × 16 ranges) and strictly
  validated (`extra=forbid`, strict types, same-space checks, non-negative
  offsets). Python re-checks every file range against the admitted size.
- Run IDs are pattern-validated and must belong to the requested version and
  profile family. Foreign runs return 404 and are never substituted.
- Responses are bounded: claims ≤64, pages ≤200, node neighborhood ≤256
  edges, node detail ≤1 MiB, previews ≤256 characters.
- Untrusted text is returned only as data fields (`label`, `preview`). The
  provided TS types mark it for escaped rendering.
- Rule matches stay observations; no score, severity or verdict fields exist.

## 14. Known limitations

- Translation joins require ghidra-4. Older Ghidra runs need a new run.
- capa joins are PE-only. YARA joins locate only the first matched byte.
  String joins require an exact start-offset match, so a reference into the
  middle of a strings-step occurrence is not linked.
- Name equality between external symbols and imports is coarse. Ordinal-only
  imports are not matched.
- Retained Ghidra windows still bound everything: 16 detailed functions
  (8 when selected), 64 instructions/calls/references.
- The graph is not pinned into reviews, and review comparison does not yet
  diff graphs.
- Linux/AMD64 host runs, hosted CI for the real lanes, and I1 remain open,
  unchanged from v0.9.

### What real tools established

- **ghidra-4 memory map, independently checked.** For PE, ELF x86-64 and
  ELF AArch64, Ghidra's own file ranges translate every string-reference
  target back to the authored literal's byte offset (`data.find`). PE
  `image_base` equals LIEF's declared ImageBase. Every file range lies within
  the input.
- **Live capa ↔ live Ghidra join.** Through the real API and worker,
  `read file via Windows API` @ VA `0x140001450` joins the Ghidra function
  `ram:140001450` by exact file offset. The expected offset comes from LIEF's
  `rva_to_offset` directly. The entry point also joins exactly. The claim
  cites that edge.
- Always-run tests reproduce this with the recorded real Ghidra documents:
  the ELF string-reference ↔ strings-step occurrence join, the KERNEL32 `ReadFile`
  name association, section placement, translation refusal for ghidra-3,
  run scoping, cursor binding, cross-database ID stability, and integrity
  failure on a tampered output.

### Defects found and fixed during verification

1. **Finding node IDs depended on database UUIDs**, so claim IDs differed
   between databases. They are now keyed on (tool, namespace, rule). Caught by
   `test_identifiers_are_stable_across_databases`.
2. **`int(text, 16)` accepted `0x`, `_` and whitespace.** Address parsing
   now requires plain hexadecimal.
3. **The real lane ran capa with stale rules.** `check-ghidra-real.sh` did not
   mount `rules/`, so the container used the image's v0.4 `/app/rules`
   (2 capa rules, no authored v0.9 rules). Real capa therefore reported no
   match for `capa_read_file` in the container. Fixed by mounting `rules/`
   read-only. The v0.9 compiled-capa acceptance itself ran on the host and is
   unaffected.
