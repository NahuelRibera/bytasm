## Requirements and implementation choices

| Blueprint requirement | Implementation |
|---|---|
| J8 / M7 structural comparison | Same logical sample and project; identity/header metadata, sections, imports, exports, strings, findings and evidence |
| Latest successful or partial analyses | Each side selects its newest succeeded/partial analysis; completed steps of partial runs remain usable |
| Provenance warnings | Incompatible tool/adapter versions, arguments, entropy method or rule snapshots prevent that category's diff |
| J7 three annotation kinds | Note, Interpretation and Conclusion, clearly marked as analyst-authored |
| Conclusions cite evidence | At least one finding/evidence citation and confidence: tentative, likely or well-supported |
| Immutable revisions | Each edit inserts a new revision and citation rows; prior revisions remain viewable |
| §6 local analyst | One seeded `local` / `Local analyst` row, without accounts or OS identity |
| J9 report changes | Schema 3 adds annotation snapshots, scope and optional comparison; old report downloads remain intact |
| Activity | Existing project/import/run events remain; annotation creation and revision emit minimal atomic events |

The blueprint leaves the exact endpoints' response shapes, limits, retry keys
and comparison export request unspecified. This implementation uses the
contracts below. Pure comparison reads are not persisted and create no events.
The read-only Tools screen is v0.3+ with no M7 acceptance criterion; it remains
later work, along with dashboard last-activity summaries and per-sample latest
run badges. Existing health/rules/run screens expose tool availability and
versions. No annotations are deleted and no approval/review state is introduced.

## Comparison

`GET /api/v1/compare?a=<version>&b=<version>&category=<optional>&offset=0&limit=50`
accepts 32-character hexadecimal version IDs. Both versions must belong to the
same sample/project (otherwise 422); unknown IDs return 404. Categories are
`metadata`, `sections`, `imports`, `exports`, `strings`, `findings`, `evidence`.
An omitted category returns all seven. Limit is 1–200, offset 0–1,000,000.

The response contains `a` and `b` (version/sample/project IDs, SHA-256, chosen
analysis ID and status), `identical_content`, `warnings`, and `categories`.
Each category has `status` (comparable/unavailable/incompatible), `reason`,
`a_status`, `b_status`, complete added/removed/changed counts, `total_rows`,
`rows` and `next_offset`. Rows contain a stable key, explicit change type,
before/after values and optional source references. References are excluded
from equality, so new database IDs never create a false change.

Matching keys:

- Metadata: named identity/header field. SHA-256, size and format are included.
- Sections: name plus sorted flags; duplicate sections are compared as sorted
  occurrence groups, not by section index.
- Imports/exports: library plus symbol, with ordinal/address as values. The
  current LIEF adapter sometimes lacks per-function library association; those
  symbols and the separately declared libraries are compared independently,
  with a warning. Bytasm does not invent associations.
- Strings: full extracted value, with sorted encoding/offset/length occurrences.
- Findings: tool, namespace and rule ID.
- Evidence: finding key, pattern, file offset and length; excerpt and XOR key
  are compared, but raw-output array positions are not matching keys.

Every displayed occurrence group is capped at 20, with total and truncation
fields; equality and change counts use the complete stored group. Truncated
string values or a capped strings extraction cannot establish equality or
absence across different bytes, so the strings category is unavailable.
Same-content comparisons retain explicit identity information and no content
changes. The comparison is static; entropy remains a measurement in bits/byte.

Import metadata comes from the successful import, independently of later runs.
Tool data comes only from successful steps of the newest succeeded/partial run.
If none exists, the most recent run's status remains visible as context, but
failed/cancelled results are not treated as empty observations. Step statuses
retain failed, timed-out, cancelled and not-run distinctions. A newer failed run
does not erase the earlier successful/partial run selected by blueprint J8.

Run selection and the version selectors normalise optional fractional seconds
before ordering ISO timestamps, preserving microsecond precision. The UI
defaults to the two newest versions (timestamp, then ID for ties), offers
category navigation and bounded pages, and links to the source version/run or
finding/evidence anchor. It presents unavailable and incompatible states,
partial-run context, and an identical-bytes notice. No verdict is inferred.

## Annotations and citations

Migration `0005` adds `analyst`, `annotation`, `annotation_citation` and nullable
`report.scope`. Existing reports keep null scope in storage; their files are
unchanged. The upgrade preserves imports, runs, findings, evidence and activity.
Downgrade removes v0.3 annotation data and scope; earlier data remains.

Each `annotation` row is one revision. `root_id` identifies the annotation;
`supersedes_id` and a unique `(root_id, revision)` chain allow only one successor.
Targets are sample versions, findings or evidence. Concrete foreign keys retain
references, and SQLite triggers reject revision/citation UPDATE and DELETE.
Application validation checks target relationships, successful source steps,
and that every citation belongs to the exact same version/project. Successfully
committed steps retained by partial/cancelled runs remain valid citation sources.
Historical citations are never silently moved to a newer run.

Text is plain, trimmed and 1–4000 characters. There are at most 20 distinct
citations. Only conclusions have confidence, and they require confidence plus
at least one citation. Text is rendered through React; no HTML/Markdown engine
or inline styles are introduced. Annotation text is never copied to activity.

API:

| Method and endpoint | Body / result |
|---|---|
| `POST /annotations` | `target_type`, `target_id`, `kind`, `body`, nullable `confidence`, `cites[] {target_type,target_id}`, optional `request_id` |
| `GET /annotations?target_type=&target_id=&offset=0&limit=25` | Current revisions for that target, `{items,next_offset}` |
| `POST /annotations/{root_id}/revisions` | `expected_revision`, `kind`, `body`, `confidence`, `cites`; target cannot change |
| `GET /annotations/{root_id}/revisions?offset=0&limit=25` | Immutable revisions, oldest first |
| `GET /sample-versions/{id}/citation-targets?offset=0&limit=100` | Bounded finding/evidence choices with source run, version and concise label |

These paths are under `/api/v1`; limits are 1–100 and offsets 0–1,000,000.
Annotation responses contain root ID, revision ID/number, target, version, kind,
text, confidence, local author, timestamp and validated citation references.
Invalid references/fields return 422 or 404 as appropriate; stale edits return
`annotation_stale` (409). All writes require the existing mutation header and
Host/Origin checks. There are no delete endpoints.

The UI sends a stable 32-hex `request_id` for retries of an unchanged creation
draft. A matching replay returns the original revision without another event;
reusing a token for different content returns 409. Revision requests include
`expected_revision`; competing edits produce one successor and reject the rest.
A failed write leaves neither a revision nor its citations/event behind.

Activity types `annotation.created` and `annotation.revised` carry only
`annotation_id`, `revision_id`, `sample_version_id`, `revision`. The activity
projection validates those references and the annotation target before linking.
It exposes nullable `annotation_target_type` and `annotation_target_id` alongside
`annotation_id`/`revision_id`; a finding/evidence target also supplies its verified
`run_id`. These are resolved from stored records, not trusted from event payloads.
Version annotations link to the version; finding/evidence annotations link to the
source run and automatically open the matching editor section (including the
evidence disclosure). Invalid or foreign targets expose no link. Event payloads
remain unchanged and contain no annotation text. Reading or comparing emits no
event; comparison is computed, not persisted.

## Reports

New exports use schema 3 at `schemas/report.schema.json`. The unchanged v2
schema is retained as `schemas/report-v2.schema.json`; previously stored reports
remain downloadable without rewriting. Existing metadata and pattern-analysis
fields retain their v2 meaning. New fields:

- `scope`: sample-version or comparison, with the included version IDs.
- `annotations`: current validated revisions for the included versions, with
  authors and citation IDs, separate from automated findings. Older revisions
  remain in the application's history; the export is a current-state snapshot.
- `comparison`: null for an ordinary export, otherwise the complete changed-key
  comparison. All API pages are gathered; occurrence-display caps remain stated.

`POST /sample-versions/{b}/reports?compare_with={a}` creates a comparison export;
without the query parameter it exports the single version as before. Version B
remains the primary metadata/pattern-analysis report; annotations include both
versions. Both blobs, import outputs, chosen analysis outputs, rule snapshots,
and cited run outputs are reverified. Broken citations or tampered storage refuse
export. Canonical JSON and stable ordering preserve reproducibility apart from
`generated_at`. Export takes SQLite's writer slot before reading, so citation
verification, comparison pages and report rendering share one snapshot; other
writes wait under the existing busy timeout. Comparison string differences can contain extracted text, so
sharing a comparison report may disclose it; single-version reports still carry
string counts only.

## Verification and limits

Focused tests cover known structural changes, deterministic grouping and paging,
identical content, missing/failed/cancelled/partial analyses, provenance mismatch,
truncation and project/sample isolation. Annotation tests cover kinds, limits,
foreign citations, immutable history, concurrent edits, idempotent creation,
rollback, and populated migration round trips. Report tests validate schema 3,
deterministic exports and tamper refusal. UI tests cover selectors, categories,
source links, validation, revisions, citations, errors and paging. A real 360 px
end-to-end test connects imports, both analyses, comparison, a cited conclusion,
revision history, activity and report download, with keyboard and axe checks.

No new binary admission mode, parser isolation claim, database, queue, account,
service or major dependency was added. No function/behavioural diff, review state,
HTML report preview, historical backfill or annotation deletion is included.
The new, currently untracked `hello_v2-x86_64.elf` fixture preserves the v1 URL and adds
`getenv`, `BYTASM_DEMO` and an environment-lookup string. The real-worker fixture
acceptance test proves exactly the added `getenv` import and the expected new
string, unchanged finding keys, and deterministic empty self-diffs. The pinned
cross-toolchain compiled v2 twice with identical bytes; no sample was executed
and the eight existing binaries were left unchanged. Rebuild details and the
SHA-256 are recorded in `fixtures/BUILD_INFO.txt` and `MANIFEST.sha256`.
