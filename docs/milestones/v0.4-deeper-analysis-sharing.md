## Run, storage and evidence contract

Import still records LIEF metadata once. Quick selects **strings → YARA-X**;
Full selects **strings → YARA-X → capa**. Input admission, current SHA-256 and
size are checked before every step, and the child rechecks hashes. A profile
snapshot records selected tool/adapter versions, timeouts, arguments and rules.
Each finished step commits in its own existing conditional transaction; only
validated successful output and its rows are persisted. The original capa CLI
JSON is content-addressed; the envelope is an internal validation contract.
No sample bytes are placed in SQLite or copied into reports.

- `succeeded`: every selected step succeeded, including valid zero matches.
- `partial`: at least one step preserved a validated result and another did not.
- `failed`: no step preserved a result. There is no inferred zero-match result.
- `cancelled`: user cancellation wins the final transition; earlier committed
  step results survive, a step still being validated/committed loses the race
  if cancellation committed first, and remaining steps are skipped.
- `unsupported` and `unavailable` are explicit **step** statuses, alongside
  `failed`, `timed_out`, `cancelled`, `skipped`, `queued`, `running`, `succeeded`.
- On restart, committed steps determine the interrupted run's terminal status;
  a run is not left permanently running. No half-written child output is used.

capa bounds: 64 MiB input, Linux 1 GiB address space, 100 CPU seconds, internal
110-second CLI deadline and parent 120-second deadline; 16 MiB per-file output
limit, 8 MiB accepted original JSON, 64 KiB accepted stderr and captured parent
streams, 16 MiB parent envelope. Maximum 16 rule observations and 32 retained
function addresses per rule (actual subset: two rules); truncation stays explicit.
Native Linux has a same-UID task limit; supported non-root Compose uses the
verified 128-task cgroup instead of a namespace-inaccurate RLIMIT_NPROC count.
Container testing caught and corrected both cross-namespace process accounting
and the upstream default cache's attempt to write a non-writable home directory.
These controls remain resource limits, **not a sandbox**. Outbound access is
not isolated. Native macOS cannot enforce RLIMIT_AS and remains fixture-only.

Only capa's static match-scope absolute addresses are normalized. A capa evidence
row has a virtual address and original JSON pointer, null byte offset/length,
and no invented name, byte excerpt, section mapping or source-code explanation.
Detailed feature trees remain in the explicit original JSON download. Parent
validation checks versions, sample/rule hashes, exact packaged source, namespaces,
classification labels, match counts, addresses and pointers before persistence.

Existing annotation scope/revision checks accept capa finding/evidence citations.
Project activity uses the existing transactional run and annotation event paths.
Comparison adds `capabilities`: equality requires the same tool/adapter versions,
rule hash and relevant args; function location changes are included. Missing or
incompatible steps do not become zero-change or zero-capability claims.

## Reports, migration and summaries

Migration **0006** adds nullable unsigned-address storage and permits null byte
ranges for capa; existing byte evidence and citations survive. Downgrade refuses
while non-byte evidence exists instead of silently destroying it. SQLite and the
single local claim-loop worker are unchanged. ADR-0002 selected SQLite for v0.1
but expected PostgreSQL for v0.2; proposed ADR-0003 documents the implemented
SQLite departure. Its status remains **proposed**: this work does not accept it
on the owner's behalf or resolve that pre-existing governance discrepancy.
WAL/busy timeout/conditional updates remain; power-loss durability and multiple
workers/hosts are not newly verified or supported.

New canonical reports use schema **4**. Published schema 2 is unchanged; the exact
schema 3 from main is retained at schemas/report-v3.schema.json. Migrations never
rewrite stored JSON; populated round-trip tests verify both v2 and v3 download
bytes and hashes. Reports select the existing newest successful/partial run and
also disclose latest failed/cancelled run context. Each finding names its own
rules hash; root YARA provenance is not mislabelled as capa's.

A version Report library and comparison preview create/reopen persisted snapshots;
React renders them as text. JSON and HTML derive from that same verified snapshot.
Jinja2 autoescapes all keys/values. HTML has no JavaScript, remote assets, forms,
event handlers or raw-HTML insertion; CSP header/meta, wrapping and print styles
are included. Legacy v2/v3 JSON remains downloadable; HTML requires schema 4.
Comparison previews/exports warn about changed strings and analyst-authored text.
See docs/report-format.md and docs/api-v0.4.md for exact contracts.

Plain-language paragraphs are deterministic English templates over validated
identity, actual selected step statuses, tool observation counts and capped string
counts. Comparisons use + added / − removed / ~ changed only for comparable data.
They are shown near the top of runs, preview and HTML; the full underlying data
remains available. Human conclusions remain separately labelled/cited. A latest
failed/cancelled run is disclosed even if an earlier result run supplies a report.
No AI, external lookup, risk percentage, safety rating or behavior verdict exists.

Run summaries show completed **selected** steps out of the selected total (including
unsupported steps), tool rule counts, stored strings and cap flags. No percentage
is invented from incomplete or zero denominators. This is a small accessible
count summary, not a new dashboard/chart suite. Tests cover missing/failed/partial/
cancelled/unsupported/capped results, comparison incompatibility and zero matches.
