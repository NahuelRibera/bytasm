## The run

### Steps (profile `default-static`, snapshot version 2)

1. **strings** — `bytasm.adapters.strings_extract` in a child process.
2. **yara-x** — `bytasm.adapters.yara_x_scan` in a child process, with the run's frozen rule-set snapshot.

Header metadata (LIEF) is read once by the import (v0.1) and is not repeated as a step; the snapshot records this as `"metadata_from": "import"`. The blueprint's example in §7.2 lists a `metadata` step; repeating LIEF on every run would add a parse of the same bytes with no new information, so it was not added. capa (the blueprint's step 4) is v0.4.

Before **each** step the worker re-runs the input policy on the sample's SHA-256, reads the stored blob, and verifies its SHA-256 and size (`bytasm.jobs.pipeline._admit`). If that fails, no tool sees the bytes and no later step runs. Each child re-hashes its input before reading it.

### Statuses

Run: `queued → running → succeeded | partial | failed | cancelled`, `queued → cancelled`.
Step: `succeeded`, `failed`, `timed_out`, `cancelled` (each recorded as a `tool_invocation`), or `skipped` (no invocation: not run). While a run is active, steps without a record show `queued` / `running`.

| Final status | When |
|---|---|
| `succeeded` | Every step succeeded. |
| `partial` | At least one step succeeded and kept its results, and at least one did not (failed, timed out, or was not run because the worker stopped or the sample failed its admission checks). |
| `failed` | No step kept results. A run is never `partial` without a preserved result. |
| `cancelled` | A cancel was requested before the run finished. Steps that finished before it keep their results. |

A failed or timed-out step does not stop the run: YARA-X does not depend on the strings step, so it still runs. A cancelled step, a failed admission check, or a stopping worker ends the run there.

### Partial-result policy

Blueprint §5.4.1/§9.1 ("Partial output is never used") applies **per step**: a step's output is used only if its child exited 0 and its result passed size, schema and content validation. Results of earlier steps survive a later step's failure: they were validated against the same verified bytes and committed on their own. This is what §3 (`partial` status), §7.3 ("Findings below come from metadata and strings only") and §9.1 ("Timeout in one step → run `partial`") describe, so there is no conflict to resolve; the first slice's "all or nothing" applied only because it had one step.

### Transactions and races

- Each step's outcome is one transaction (`pipeline._record`). For a succeeded step, its first statement is a conditional `UPDATE analysis_run … WHERE status = 'running' AND cancel_requested = false`; in SQLite that statement also takes the write lock, so a cancel committed before it turns the step into `cancelled` (nothing stored), and a cancel arriving after it waits for the commit and then applies to the rest of the run. The raw output file is written inside that transaction and removed if it does not commit.
- The final status is one conditional `UPDATE … WHERE status = 'running' AND cancel_requested = false`; if a cancel arrived, the run becomes `cancelled` instead. Terminal states never change.
- Timeout vs cancel: the runner classifies one outcome per child; exactly one invocation per step is recorded (tested with a cancel landing next to a 1 s deadline).
- Worker stop (SIGTERM): the current child's group is killed, the step is recorded `cancelled` (`worker_interrupted`), and the run ends `partial` or `failed`.
- Worker restart: runs left `running` are finished from their committed steps — `partial`/`failed` with `worker_interrupted`, `cancelled` if a cancel had been requested, `succeeded` if every step had committed. A run never stays `running`.
- An exception inside the pipeline ends the run from its committed steps with `internal_error`.

### Strings extractor

- **Definition** (`adapters/strings_result.py`): `ascii` = ≥ 6 bytes in 0x20–0x7E or tab; `utf-16le` = ≥ 6 code units "printable ASCII or tab, then 0x00". Newlines and other control bytes end a run. Any byte alignment; no overlap within one encoding; the two encodings are searched independently. UTF-16 text outside ASCII is not extracted. These are the blueprint's encodings and minimum length; "printable ASCII" is the conventional `strings`/`strings -e l` definition, chosen because every value is then one line of plain text.
- **Bounds:** input ≤ 64 MiB (the upload limit); at most **5,000** strings kept (the first by offset; the total found is still counted, `truncated`); each value cut to **256** characters with its full length reported; the same child limits as LIEF (RLIMIT_AS 1 GiB, CPU 25 s, 30 s wall clock, 32 MiB result, 64 KiB captured streams). Measured worst cases at 64 MiB on this host: 1.3–2.9 s.
- **Order and fields:** sorted by (offset, encoding); `offset`, `encoding`, `length_chars`, `byte_length`, `value`, `value_truncated`.
- **Validation in the parent** (`jobs/strings_step.py`): schema with `extra="forbid"`; input hash and size; counts add up; `truncated` consistent; strict order; each item's byte range is a complete printable run of that length inside the file, and its value equals those bytes decoded. Any mismatch rejects the whole result.
- **Storage:** `string_occurrence` rows tied to the invocation; no sample bytes in the database. Strings are observations: they never become findings, and no string is labelled.
- **Display:** React text only (the existing lint ban on raw-HTML APIs applies); values wrap anywhere inside a horizontally scrollable table region. Not logged; not exported in the report (counts only).

### Raw output download

`GET /api/v1/invocations/{id}/raw` serves the **validated `result.json`** a step's adapter wrote, as stored in the content-addressed outputs store (≤ 32 MiB by the runner's cap; in practice kilobytes), re-hashed before serving, as an `application/json` attachment with `nosniff`. It is what `raw_json_pointer` points into. It never contains the sample bytes, stdout or stderr; failed steps have no raw output (404). This is the blueprint's "link to the raw output file" (J6), needed to check a finding's provenance by hand.

## Database

- **What the documents decide.** Blueprint §5.4 says "Database: PostgreSQL" as a plan; ADR-0001 §7 records the database as "**Undecided as a formal decision**". ADR-0002 (**accepted**) chose **SQLite** for v0.1 and *expected* the v0.2 worker to need PostgreSQL. §5.4.2 deferred the worker choice to v0.2 ("Procrastinate or a hand-rolled claim loop", both described on PostgreSQL). So PostgreSQL is not an accepted requirement; whether the v0.2 queue may stay on SQLite is an open decision, proposed in ADR-0003 and **not accepted**.
- **What the implementation does.** One SQLite file in WAL mode (`PRAGMA journal_mode = WAL`), `foreign_keys = ON`, 30 s busy timeout, shared by `bytasm serve` and one `bytasm worker` (enforced by `flock` on `data/worker.lock`). Every run transition is a conditional `UPDATE`; SQLite serialises writers, so the conditional update is the claim. Run creation and its job are one row in one transaction, the property §5.4.2 asks of either option.
- **Evidence (tests in this repository):** conditional transitions and claims (`test_transitions_are_conditional_on_the_current_state`); the cancel-vs-commit gate (`test_a_step_result_is_not_stored_once_cancel_was_requested`, the three cancel-race tests); API and worker as separate OS processes over HTTP on one database (`test_live_server_and_worker_process_complete_a_run`, Playwright e2e); restart recovery (`test_worker_restart_never_leaves_a_run_running`); atomic migrations with rollback on failure (`test_migrations.py`). Durability after power loss and behaviour under heavy concurrent writers were **not** tested; WAL with SQLite's default `synchronous` setting is assumed adequate for a local single-user tool.
- **Limits of this choice:** one worker per data directory; polling (0.5 s) instead of `LISTEN/NOTIFY`; not suitable for several workers or hosts. Moving to PostgreSQL would change the engine, the claim query (`FOR UPDATE SKIP LOCKED`) and the migration dialect, not the lifecycle.
- **Not changed here** to silence the discrepancy: switching engines needs the owner's decision (ADR-0003).

## Known limitations

- **Not a sandbox.** Both tools run as the worker's user with the worker's files (including the database) and network. Inputs stay self-authored (fixtures, or `self_built` natively on Linux). Not gate I1.
- **SQLite queue:** see "Database". One worker per data directory; polling (worker 0.5 s, UI 2 s).
- **One run per sample version at a time;** runs on different versions queue behind each other.
- **Rule validation shares the single parser slot** with imports (503 while an import parses).
- **Evidence is byte ranges only** (no section or virtual address yet); at most 20 per pattern, 32 bytes each.
- **Strings:** printable ASCII in two encodings only; values cut at 256 characters; at most 5,000 per run; the report carries counts, not values.
- **`upx_style_section_name`** has no positive fixture; the corpus only proves it does not match Bytasm's fixtures. Every fixture now matches at least one rule, so "no match" is tested with a test rule set and UI unit tests.
- **Timestamps** have one-second resolution; the technical log orders entries by lifecycle, not by clock.
- **linux/amd64 not run locally**; hosted CI on x86-64 runners would cover it after a push.
- **Native macOS:** RLIMIT_AS is not applied to the strings or YARA-X child either.

## Project creation audit (2026-10-28)

Migration `0004` adds `activity_event` with a project foreign key and index.
Creating a project inserts exactly one `project.created` event in the same
transaction, with the same UTC timestamp. `actor_id = "local"` denotes the
single local operator, without accounts or an OS identity. The payload is
always `{}`: no project text, request metadata, file contents or secrets.
Events are append-only in application code; direct database writers are not
prevented from changing them. Existing projects are not backfilled. Downgrading
to `0003` removes audit events and preserves projects and analysis data.

Tests cover one event per creation, reads emitting no events, rollback when
either insert fails, preservation of existing rows through upgrade/downgrade,
and agreement between the migrated schema and ORM models. All databases used
for these tests are temporary.

## Import audit (2026-10-29)

Each successful import records `sample_version.imported` in the import's
transaction, including when adding a version to an existing sample. Its payload
contains only `sample_id` and `sample_version_id`; the actor is `local` and the
timestamp is the version's `imported_at`. The event name and payload were chosen
for this slice; the blueprint defines the audit table but no import event name.
No schema migration or historical backfill is needed. Refused inputs, parser
failures and rolled-back imports leave no success event. Tests cover both sample
targets, the exact payload, and failures in row insertion, storage and commit.
